# Galatea – Second Life AI avatar

Handoff kit so another AI agent can help run or improve an AI-run avatar in Second Life. Home base: The Buddha Center, region **Naberrie**.

See [TESTING.md](TESTING.md) for how to run the automated test suite locally (C# xUnit + pytest). CI runs on every PR and on `main`.

**Impact-based local test runs** (Oct 16, 2026; David: "do you always need to run all 602 tests?"): `python3 scripts/impact_tests.py` maps the current diff (against `origin/main`, plus uncommitted and untracked files) to the tests that can be affected and runs only those; `--dry-run` shows the selection and why, `--full` runs everything CI runs, `--commit SHA --dry-run` analyses a past merge. It tokenises every C# file under `textclient/`, splits it into members, finds the changed members from the diff's line ranges, follows who uses them (reverse closure over names, narrowed by `Type.member` qualifiers, private access, the receiver's declared type and call arity), and selects the `[Fact]`/`[Theory]` methods reached; `--*-selftest` flags in `Program.Main` are nodes too, so `SelftestCliTests` shrinks to the flags whose code changed. Data and script files (routes JSON, `.py`, `.sh`) map to the code and tests that name them; Python changes run the pytest files that mention them; docs-only changes run nothing; a changed client source is always compiled (by `dotnet test`, or by `build-all.sh` when a selected test uses the built binary or no test covers it). It falls back to the **full suite** for project, build and CI files, unparsable C#, a changed file nothing references, or a selection above 60% of all tests. It is a local speed-up only: **CI still runs the full suite unchanged** on every PR and on `main` (the safety net). Tests for the mapper: `textclient/tests/test_impact_tests.py` (runs in the CI pytest job). Details in [TESTING.md](TESTING.md).

What Galatea can do and how to drive it (CLI and MCP tools): [docs/capabilities.md](docs/capabilities.md).

**Keeping docs current**: whenever a capability is added or changed, update this README and [docs/capabilities.md](docs/capabilities.md) in the same pull request.

### Texture cache
All renders fetch textures through `vision/cloud-render/handler.py` (`fetch_tex` / `fetch_textures`), modelled on the viewer's texture cache: the **raw JPEG2000 bytes** are kept once per UUID in `<work>/tex-raw/<first hex digit>/<uuid>.j2c`, and each size is **decoded from them** into `<work>/tex/<uuid>.<size>.png` (lossless, PNG level 1). A different size or discard bias (it follows free memory) therefore costs a local decode, not a download. Both tiers are capped (2 GB each by default) and evict the oldest-used files down to 80% when over; a hit refreshes a file's age. Decoding runs on a process pool (PIL holds the GIL). A texture the CDN never answers is remembered for 6 h in `tex/.missing.json`, so it no longer costs a 20 s timeout per photo. The old uncapped `<uuid>.png` files are deleted once per work dir (marker `.legacy-retired`); bakes and `.missing.json` are never touched. Measured on the Peronaut scene (3,254 textures): texture stage 157 s cold / 21 s warm / 79 s after a bias change before, about 78 / 0.5 / 11 s now. **Other caches** are kept separate on purpose (different writers, keys and formats) but now share the same policy, applied at the end of every `look.py` run (`handler.prune_aux_caches`): a size cap, oldest-used first down to 80%, nothing younger than an hour. The client's raw bake cache (`GT_BAKE_CACHE`, default `/workspace/secondlife/vision/bake-cache`, cap `GT_BAKE_CAP_MB` 2048), the decoded bake cache (`<work>/bakecache`, cap `GT_BAKECACHE_CAP_MB` 512; a hit refreshes the file's age) and the scene-mesher asset cache (`SCENE_MESHER_CACHE`, default `~/.cache/scene-mesher`, cap `SCENE_MESHER_CACHE_CAP_MB` 2048; the mesher refreshes a file's age on a hit, so rebuild/deploy it for true oldest-used order, until then it is oldest-written). Not merged into `tex-raw/`: bakes are the client's own bake ids (the client writes them, Python never downloads them) and the mesher's cache holds meshes, animations and materials (only 55 sculpt maps are textures), so sharing would save no download. The C# texture vision (`texture save`, `faces`, `vendor look`) writes user-facing full-size PNGs from the logged-in session and keeps its own per-session cache; it is unchanged. Test: `vision/tests/test_texture_cache.py`.

**Memory** (4K HD, measured 2026-10-14 on the Peronaut home scene, ~1.0 M triangles, Ultra): Blender alone costs about 3.2 GB (`HD_OVERHEAD_MB`) on top of the scene and its textures; the peak was 6.5 GB with one denoise band and 5.8 GB with three (`look.py` picks 1-3 `GT_HD_BANDS` and a texture budget `GT_TEX_BUDGET_MB` from the free memory). A 96 m export peaked at about 7 GB, so plan on roughly 7-8 GB of free memory for the render itself, on top of the guard floor below; the client chooses the export radius from free memory (256 m with 14 GB free, 128 m with 10 GB, else 96 m). `GT_MEM_FLOOR_MB` (default 1500) is a memory guard: if the box's `MemAvailable` drops under it the render is SIGKILLed so the box (and the client's UDP reads) stay responsive. A signal death (`-9`) is retried up to twice with a higher texture discard bias, a smaller texture budget, `GT_TEX_LIMIT=1024` and smaller tiles (`GT_TILE` 512, then 256); a plain crash is rerun once. One look runs at a time. **Crowds (layered `photo hd`, Oct 18, 2026):** a 4K render of a packed venue (Warehouse 21: ~3.3 M world vertices plus ~7 M avatar vertices) cannot fit one Blender process, so `look.py` renders it in layers ([`vision/layers.py`](vision/layers.py)): a *base* pass (world + her; the other avatars are shadow-only stand-ins that light and shade but are never seen) and then *batch* passes of a few of the other avatars each, nearest-to-camera last, every pass a separate Blender process (so its memory is freed before the next) with the same camera, lens, depth of field, sun and sky. In a batch pass the world and her are Cycles **holdouts** (they hide the batch's avatars exactly where they stand in front, and still cast shadows and bounce light), the film is transparent, and the result is premultiplied RGBA that is **avatars only**: no sky, world background or haze colour in any pixel, edge pixels included (a flat background behind a layer, or a per-pixel mist haze, tinted a pale sky-blue fringe round blurred background avatars, fixed Oct 18, 2026). The distance haze in front of a batch's avatars is added once per layer when `look.py` composites, as one fog fraction from the layer's solid pixels (`-haze.json` next to the layer). `look.py` alpha-composites the batches over the base **back to front** in scene-linear light, then glow, tonemap and sharpen run once on the finished frame, so the PNG/JPG/EXR/HDR outputs are the same as a single-pass photo. Occlusion is exact for the world and for her and correct *between batches* by depth order (nearer batch on top); the one approximation is two avatars from different batches that interleave in depth (an arm of one in front of the other's body while its centre is farther), where the nearer-centre avatar wins whole. Front-to-back rendering with holdouts of the nearer avatars was rejected: each pass would have to hold every nearer avatar again as a holdout, so memory grows with the crowd instead of staying flat. Cycles' light-tree build was most of a pass's peak (about 3 GB of 5 GB), so emissive faces of the holdout world, and of the base world beyond 25 m, are not importance-sampled. It switches on by itself when world + all avatars would not fit the free memory (`GT_HD_LAYERS=on|off|auto`); a batch killed by the memory guard is split in two and retried, and an avatar that still fails is left out with a warning. Per-pass peak memory and time are in the look summary (`layers`) and each pass's log is kept in `look-work/layers/pass-N.log`.
